# F4: 集成实战经验与坑

## Findings

### [1] esptool-js 官方提供两种集成方式：CDN 单文件 `https://unpkg.com/esptool-js/bundle.js`（已内联 pako 等依赖，无需 import map）与 npm 包 `esptool-js`；浏览器按原生 ESM 使用 lib/index.js 时必须配置 import map 映射 pako、atob-lite 裸标识符
- quote: "Use `https://unpkg.com/esptool-js/bundle.js` for a single-file browser load. Dependencies such as pako are inlined, so no import map is required."
- url: https://raw.githubusercontent.com/espressif/esptool-js/main/README.md
- source_type: primary
- published: 2026 (v0.7.0 era)
- confidence: high

### [2] esptool-js 核心 API 流程固定为五步：requestPort() → new Transport(port, true) → new ESPLoader({transport, baudrate, terminal}) → esploader.main() 检测芯片（会触发复位）→ writeFlash({fileArray, flashMode/flashFreq/flashSize, compress, reportProgress}) → after("hard_reset")；烧录地址（如 0x1000）由调用方显式指定，库不解析 ELF
- quote: "const chipName = await esploader.main(); ... await esploader.writeFlash(flashOptions); ... await esploader.after(\"hard_reset\");"
- url: https://raw.githubusercontent.com/espressif/esptool-js/main/README.md
- source_type: primary
- published: 2026
- confidence: high

### [3] 真实失败案例一（芯片检测）：ESP32-C5 rev1.2 (ROM eco3-20250704) 返回 CHIP magic 0x30e1706f，不在 esptool-js 0.6.1 的 ESP32C5ROM.CHIP_DETECT_MAGIC_VALUE 列表内，detectChip() 直接报错 "Unexpected CHIP magic value... Failed to autodetect chip type"；同端口 Python esptool 5.3.0 用 GET_SECURITY_INFO 正常识别——Web 方案的芯片识别能力滞后于 Python 版，v0.7.0 以 GET_SECURITY_INFO 检测（PR #197）修复
- quote: "Unexpected CHIP magic value 0x30e1706f. Failed to autodetect chip type."
- url: https://github.com/espressif/esptool-js/issues/262
- source_type: community (issue) + primary (修复)
- published: 2026-09-02 (opened), 2026-09-22 (closed)
- confidence: high

### [4] 真实失败案例二（高波特率大读取）：readFlash() 大容量读取（整分区备份）会在传输中途失步失败，报告者称降低波特率"有时"能走得更远；日志显示连接后自动切换到 460800 波特率——高波特率 + Web Serial 缓冲是稳定性敏感点，issue #218 截至 2026-09 仍 open
- quote: "It fails when doing large reads... If I try with a reduced baud rate it sometimes gets further... It seems something with the serial protocol is getting out of sync."
- url: https://github.com/espressif/esptool-js/issues/218
- source_type: community
- published: 2025-11-07 (opened), still open at 2026-09-22
- confidence: high

### [5] 真实失败案例三（复位时序）：部分设备的复位电路对 DTR/RTS 变化敏感，逐条 await setDTR()/setRTS() 产生的调度延迟足以让复位失败；esptool-js 在 v0.7.0 引入 Transport.setSignals() 一次性同时设置信号（PR #225，修复 issue #222）——早期版本集成者需自定义 resetConstructors 规避
- quote: "Some devices have a reset circuitry that are sensitive to slow RTS/DTR changes. The current await this.transport.setDTR() and await this.transport.setRTS() seems to cause enough delay on some platforms to make the reset fail."
- url: https://github.com/espressif/esptool-js/issues/222
- source_type: community + primary (修复)
- published: 2025-11-25 (opened), 2026-09-21 (PR #225 merged)
- confidence: high

### [6] 自定义复位序列已是一等公民：esptool-js 支持以 "D0|R1|W100|D1|R0|W50|D0" 格式的字符串声明自定义 DTR/RTS 复位序列（D=setDTR, R=setRTS, W=等待ms），并提供 classicReset/hardReset/usbJTAGSerialReset 内置策略与 validateCustomResetStringSequence 校验——硬件不标准时的官方逃生舱
- quote: "const customResetSequence = \"D0|R1|W100|D1|R0|W50|D0\";"
- url: https://raw.githubusercontent.com/espressif/esptool-js/main/README.md
- source_type: primary
- published: 2026
- confidence: high

### [7] 部署硬约束（集成时最常踩）：Web Serial 要求 HTTPS（localhost 除外）；跨域托管 manifest/固件必须配 CORS 头；esp-web-tools 明言"your website must be served over https://... This is a Web Serial security requirement"
- quote: "ESP Web Tools requires that your website is served over `https://` to work. This is a Web Serial security requirement."
- url: https://esphome.github.io/esp-web-tools/
- source_type: primary
- published: 2026
- confidence: high

### [8] ESP-IDF v4+ 四段式固件（bootloader/partition-table/app/初始化数据）必须先用 esptool merge_bin 合并成单 bin 才能走 esp-web-tools，因为它无法像命令行 esptool 那样烧录时动态修补 flash 频率/大小/模式字节——构建流水线要多一步合并工序
- quote: "ESP Web Tools is not able to do this on the fly, so you will need to use `esptool` to create the single binary file and use that with ESP Web Tools."
- url: https://esphome.github.io/esp-web-tools/
- source_type: primary
- published: 2026
- confidence: high

### [9] 烧录后遗症案例：有用户报告"烧录成功但板子无响应"（issue #201，已关闭）——web 烧录的完成判定（writeFlash 成功）与固件可运行是两回事，还需正确的 hard_reset 与固件本身有效性
- quote: "After flashing the firmware, the board remains unresponsive."
- url: https://github.com/espressif/esptool-js/issues/201
- source_type: community
- published: 2025-05-21 (opened), 2026-09-21 (closed)
- confidence: medium

### [10] 串口互斥：Web Serial 一次独占一个端口，页面需处理 connect/disconnect 事件与用户已授权端口列表 getPorts()；桌面 OS 驱动占用（CH340 场景）会导致 claimInterface 失败，这是 esptool-js 增加 WebUSB 实验通道的直接原因
- quote: "桌面 OS 内核 usbserial 驱动常占用 CH340 导致 Web Serial claimInterface 失败"
- url: https://espressif.github.io/esptool-js/ (demo, F1 finding [5]) 与 PR #271 changelog
- source_type: primary
- published: 2026-09-21
- confidence: medium (综合两处来源)
