# 04 · 参考方案对照

> 用途：评估取舍时的外部坐标系。  
> 说明：本篇基于既有产品认知整理；部分条目未在撰写日做实时核实，**把握度**已标注。若需立项引用，请再核对官方文档。

---

## 1. 对照维度

围绕本项目真实差异点：

1. **烧录端要不要账号**（Web Serial 在用户本机）  
2. **固件/产物怎么归属**（谁的库）  
3. **如何授权他人使用**（公开 / 成员 / 链接）  
4. **机器发布用什么凭证**  
5. **团队如何共管**

---

## 2. 四类邻居产品

### 2.1 A · 网页烧录工具（无身份的工具站）

| 产品 | 身份 | 固件来源 | 可借鉴 | 把握度 |
|---|---|---|---|---|
| ESP Web Tools（esphome） | 无 | 站点 manifest | Web Serial 烧录交互、manifest 载入 | 高 |
| ESP Launchpad（乐鑫） | 无 | 云上固件列表 | 官方网页烧录形态 | 高 |
| Adafruit Web Serial Flasher | 无 | 固定清单 | 极简可靠路径 | 中 |

**结论**：烧录端普遍无账号——印证「工具本体不该被登录打扰」。  
它们解决「怎么烧」，**不解决「谁的固件库」**。

### 2.2 B · 设备云 / OTA（强账号、强管理）

| 产品 | 身份 | 多人 | 可借鉴 | 把握度 |
|---|---|---|---|---|
| Memfault | SaaS 账号 | 组织/项目/角色 | 工业级角色与 fleet | 中 |
| Balena | 账号 | fleet/member | 设备身份与应用边界 | 中 |
| ESP RainMaker | 账号 | 有 | 乐官方 IoT 路线 | 中 |
| Mender | 账号 | 组织 | 自托管 OTA | 中 |
| Arduino IoT Cloud | 账号 | 有 | 消费级体验 | 中 |

**结论**：一旦管「设备 + 固件 + 团队」，无人敢完全匿名。  
但本项目 **P0–P2 不以设备 fleet 为中心**，避免过重。

### 2.3 C · 产物仓库 / 发布分发（最像 registry）

| 产品 | 身份模型 | 私有/公开 | 机器凭证 | 可借鉴 | 把握度 |
|---|---|---|---|---|---|
| Hugging Face Hub | 账号 + token | 仓库级 | fine-grained token | 现代 artifact hub 范本 | 高 |
| GitHub Releases/Packages | 账号 + PAT | repo 可见性 | fine-grained PAT | 与 `wk_` 模型同构 | 高 |
| npm / PyPI / Docker Hub | 账号 + API token | 可私有 | 长寿命 token | 写用 token、读看公开性 | 高 |
| PlatformIO Registry | 账号 | 库可见性 | 有 | 嵌入式生态接近 | 中 |
| Gitee | 账号 | 可私有 | 有 | 国内部署语境 | 高 |

**结论**：主流答案 = **账号负责归属，token 负责机器写入**。  
这正是本项目 03 章模型。现有 `tools/publish` + Bearer 已经是半个 PyPI token 形态。

### 2.4 D · 链接/分享码（授权便利，不是产品）

| 机制 | 身份 | 适用 | 弱点 | 把握度 |
|---|---|---|---|---|
| 网盘分享码 | 无/弱 | 传文件 | 无成员、难按人回收 | 高 |
| WeTransfer 类 | 邮箱可选 | 限时大文件 | 不管版本 | 高 |
| S3/R2 presigned URL | 签名过期 | 受控下载 | 无订阅关系 | 高 |
| Keygen（license key） | 密钥即用户 | 软件授权 | 偏许可 | 中 |
| 魔法链接 | 邮箱 | 无密码登录 | 依赖邮件 | 高 |

**结论**：能解决「谁能下」，**不能解决「谁的仓库、谁在发布、团队角色」**。  
故只作为 P1 私有库授权工具，不承担主产品。

## 3. 身份方案评分（针对本项目）

| 方案 | 归属唯一仓库 | 角色/团队 | 撤销审计 | 防滥用 | 实现成本 | 总评 |
|---|---|---|---|---|---|---|
| 纯分享码 L1 | △ | ✗ | △ | △ | 低 | 不满足目标 |
| 邮箱魔法链接 L2 | ✓ | ✓ | ✓ | △ | 中 | **P0 首选之一** |
| API token L3 | ✓ | ✓ | ✓ | △ | 低 | **机器侧必须** |
| OAuth L4 | ✓ | ✓ | ✓ | ✓ | 中 | **P0 首选之一** |
| 完整账号 L5 | ✓ | ✓ | ✓ | ✓ | 高 | 可后置 |

推荐组合：

- **人**：L2 或 L4  
- **机器**：L3  
- **私有库授权**：L1（链接优先，码为辅）

---

## 4. 可直接借鉴的设计点

1. **HF / GitHub 的「登录 + 长寿命写 token」分离** → 映射 publish token。  
2. **仓库可见性三档（private/internal/public）** → 映射项目 visibility。  
3. **fine-grained token 限定范围** → publish token 可限项目。  
4. **深链打开资源（HF file / GitHub blob）** → 映射 `/p/<id>` 预载项目进工作站。  
5. **撤销即失效** → 授权链接与 token 都要即时撤销语义。  
6. **Web Serial 工具站无登录** → 工作站主路径保持低打扰。

---

## 5. 明确不抄的

| 做法 | 原因 |
|---|---|
| Memfault 式设备 fleet 重管理 | 超出「便携工作站」定位 |
| 网盘式以分享码为唯一产品 | 无仓库归属、无发布闭环 |
| npm 式强制 2FA 全员 | 小团队阶段过重 |
| 一开始做计费与配额硬墙 | P0–P2 不需要 |

## 6. 本地类比（帮助取舍）

| 若你熟悉 | 本项目对应 |
|---|---|
| GitHub：账号 + repo + PAT + private/public | 用户 + 固件库 + publish token + 可见性 |
| HF Hub：模型文件 + space + token | 固件包 + 工作站 + 发布凭证 |
| VS Code Remote / Code Server | 免安装工作站（Web Serial 版） |

一句话产品定位：

> **「带 Web Serial 工作站的多租户固件 Hub」**，不是 OTA 云，也不是网盘。
