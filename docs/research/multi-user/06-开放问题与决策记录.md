# 06 · 开放问题与决策记录

> 用途：回顾讨论如何收敛、哪些被否、哪些仍待你拍板。  
> 状态：调研备忘

---

## Part A · 决策记录（按讨论顺序）

### A1. 多人化争的是固件库，不是 Web Serial

- **背景**：烧录/日志发生在各人本机浏览器 + 自己的 USB。  
- **结论**：多人设计集中在云端 registry / 发布 / 权限；烧录端天然单人。  
- **影响**：工作站几乎不为「多人」改；重心在 server 与归属。

### A2. 「开放服务」要分阶段，不要一步到位

- **背景**：曾按对外开放评估账号、租户、配额、合规。  
- **结论**：全量开放是产品化跃迁，成本一个数量级；应先个人闭环 → 团队 → 开放。  
- **影响**：路线拆成 P0–P3，P0 只服务「第二个真实用户」。

### A3. 身份语义必留，账号形态可轻

- **背景**：希望不做账号，但服务端固件要可归属。  
- **结论**：砍「注册-密码-个人中心」，不砍「可指向、可撤销、可审计」。  
- **影响**：P0 允许魔法链接/OAuth；publish token 走 L3。

### A4. 站点结构选「同域双门」，否决全整合与独立站

- **背景**：问「发布者页面是否整合还是独立网站」。  
- **结论**：一套后端一个域名；`/` 工作站 + `/console` 管理面。  
- **影响**：运维省一套；权限按路由组区分。  
- **修正**：双门指呈现分离，**不是**下载者/发布者两套产品（见 A6）。

### A5. 概念要隐藏，门槛要低

- **背景**：反馈「账号、token、分享码对新用户都是门槛」。  
- **结论**：主路径只暴露必要概念；token 只活在 CLI；账号只在管理面；分享码降为找回。  
- **影响**：UI 文案与信息架构约束（见 02 反模式）。

### A6. 产品是便携工作站，不是下载页（重要修正）

- **背景**：简化过头画成「链接→下载列表」，被指正砍掉了产品本体。  
- **结论**：便携下载、免安装、一键下载、调试、日志查看/复制/导出、软件擦除等**全部保留**；  
  多人方案只决定「固件库怎么进工作站」。  
- **影响**：禁止「下载访客残血模式」；深链进完整 IDE。

### A7. 分享码不是目标需求，只是顺带（最终定案）

- **背景**：回到最开始目标。  
- **定案表述**：

> 从面向我自己使用，走到别人可以有与我相同的使用体验，  
> 不必自己部署，即可完成**发布、下载**。  
> 分享码最多是顺带。

- **影响**：
  - 产品 = **托管固件工作站**（体验对等）  
  - 账号 = 服务「每人唯一仓库」  
  - 分享码 = P1 私有库授权工具  
  - 否决「下载访客 / 分享码主路径」叙事

## Part B · 被否决的方案（防走回头路）

| 方案 | 否决原因 |
|---|---|
| 完全无身份，纯公开货架 | 无法归属仓库、无法授权私有库、无法团队 |
| 分享码当产品主入口 | 违反目标（要发布+下载闭环） |
| 下载用户残血 UI | 违反体验对等 |
| 首页「输码或登录」 | 门槛外露 |
| 一开始完整注册+密码体系 | 与「简单」冲突；形态可后置 |
| 独立控制台网站先上 | 过早双站运维 |
| 全塞进 IDE 五区 | 管理能力污染工具 |
| 抄设备云（Memfault 式） | 超出便携工作站定位 |
| 计费/配额硬墙放 P0 | 过早 |

## Part C · 仍待你拍板（阻塞 P0 立项）

### C1. 登录形态（三选一或组合）

| 选项 | 优点 | 代价 |
|---|---|---|
| 邀请开号 | 最快可控 | 不算开放 |
| 邮箱魔法链接 | 无密码 | 依赖邮件 |
| GitHub OAuth | 开发者体验好 | 依赖外部 IdP |

**建议**：P0 用邀请开号或魔法链接，P1 加 OAuth。

### C2. 仓库命名与寻址

| 选项 | 说明 |
|---|---|
| `userId/slug`（类 HF） | 天然唯一，迁移清晰 |
| 全局唯一 slug | 短，但会抢名 |
| 仅内部 id + 显示名 | 最简单，链接难看 |

**建议**：`owner/slug`，显示名与 slug 分离。

### C3. publish token 范围

| 选项 | 说明 |
|---|---|
| 用户级 token，可发任意自有项目 | 方便 |
| 项目级 token | 更安全，生成略繁 |

**建议**：P0 用户级；P1 支持项目级（细粒度）。

### C4. 公开项目是否强制登录可用

| 选项 | 说明 |
|---|---|
| 公开库匿名可烧录 | 门槛最低，固件易被拖走 |
| 公开库也需登录 | 可审计，门槛略高 |

**建议**：P0 允许匿名读公开库（体验对等优先）；P1 收紧下载直链。

### C5. 自用模式是否保留单机部署

| 选项 | 说明 |
|---|---|
| 双模式（托管 + 私有部署） | 灵活，测试矩阵大 |
| 只托管 | 简单，失去私有部署 |

**建议**：代码上保持可私有部署（零依赖 server 优势），文档主推托管。

### C6. 备案与域名

- 对外服务是否需要国内备案？是否用独立域名？  
- 属于运维/合规决策，不影响 P0 代码形态，但影响 P3。

## Part D · 术语表（讨论中易混）

| 术语 | 在本项目指 |
|---|---|
| 工作站 | 现有 IDE 五区 Web 工作具（烧录/日志/擦除/导出） |
| 仓库 / 项目 | registry 中的 Project（含 variant/release） |
| 发布者 | 有仓库、能发布的人（其实所有用户都可能是） |
| 下载用户 | 讨论中临时概念；**目标态不存在此角色**，只有「完整用户」 |
| 分享码 | 私有库授权的便捷凭证（顺带） |
| publish token | 编译机写发布的机器凭证 |
| 主 token | 服务器运维凭证，不出产品 UI |
| 体验对等 | 任何用户工具能力一致，无残血模式 |
